## device_info_plus-9.1.0-ohos-1.0.0-beta.2

* Consistency
The most prominent issue was inconsistent naming conventions: the method in the native DeviceMethodHandler was declared as DeviceInfoAssemble (uppercase initial, violating ArkTS/JS camelCase conventions—a critical issue). After repeated IDE/lint modifications, this even caused a compilation break where the call site this.DeviceInfoAssemble() didn't match the declaration deviceInfoAssemble(). This has now been unified to the lowercase-initial deviceInfoAssemble, with declarations, call sites, and documentation {@link} references all aligned, confirmed with grep that no uppercase remnants remain.

Secondly, a semantic consistency issue was removed: earlier attempts added try-catch for serial/udid (treating them as "system API permission insufficient"), but @ohos.deviceInfo actually has no corresponding API at all—this incorrectly treated "nonexistent" as "permission-restricted," causing documentation to contradict the code. This has been unified: the native layer does not write these two fields (with comments explaining why), the model layer retains String? (for cross-platform consistency), and documentation explicitly marks them as no (unavailable) with guidance to use odID as the device identifier. Regarding naming format, the inconsistency between the root-level README_OpenHarmony.md (underscore) and the package-level README.OpenHarmony.md (dot) was left untouched per your decision, while the EN/CN versions within the package are now internally consistent.

* Memory Leaks
The native DeviceInfoPlusOhosPlugin already correctly handled onDetachedFromEngine by calling setMethodCallHandler(null) and nullifying the channel reference upon detachment, preventing MethodChannel callbacks from hanging after engine destruction—this was already implemented correctly and was not modified in this round.

What was truly supplemented on the testing side was protection against global singleton leakage: DeviceInfoPlatform.instance is a global singleton shared across test files. Multiple test files calling registerWith() or injecting fake platforms would pollute each other, causing subsequent tests to retrieve the wrong platform instance. In this round, tearDown was added to three locations—device_info_plus_test, device_info_plus_windows_test, and device_info_plus_linux_plugin_test—unifying the reset of instance back to MethodChannelDeviceInfo. The iOS model tests also received matching tearDown cleanup paired with setUp. On the Dart side, the DeviceInfoPlugin's field caches (_cachedAndroidDeviceInfo, etc.) are reused within a single instance and reclaimed with the instance itself—no leakage risk, so no additional changes were made.

* Documentation Quality
Both EN and CN READMEs were completely rewritten, primarily addressing five categories of deficiencies. The version correspondence table was upgraded from a numbered list to a standard table with a "Third-party Library Version (device_info_plus 9.1.0)" column, with two new sections added: "Incompatibility Notes" and "Upgrade Migration Guide." The call flow was expanded from merely "add dependency + example link" to inline code (import → instantiate → await ohosInfo → read fields), with a completely new "OHOS Environment Configuration" section (DevEco installation, OpenHarmony SDK configuration, Flutter-OHOS branch, build and run). Interface properties now include previously omitted serial, udid, and fromMap. Nullability annotations were systematically corrected in the property table from String/int to String?/int?, matching the actual Dart model signatures to prevent users from overlooking null risks. The "Known Issues" section honestly documents the root cause of serial/udid unavailability on OHOS (@ohos.deviceInfo lacks corresponding APIs).

Additionally, native code documentation comments were supplemented: DeviceMethodHandler's onMethodCall/deviceInfoAssemble/replyError and DeviceInfoPlusOhosPlugin's class comment, getUniqueClassName/onAttachedToEngine/onDetachedFromEngine—totaling 5 public methods—along with parameters like call/result/binding all received /** */ with @param/@returns.

* Test Coverage
Starting from "main entry class 0/9, OhosDeviceInfo 0/36" coverage, the overall VM coverage reached 96.7% (384/397 lines) with 77 passing tests. New additions include: ohos_device_info_test (36-field fromMap + ODID case-sensitivity boundaries + empty/null), device_info_plus_test (9 getters, caching, concurrency, exception propagation, MethodChannel mocks), device_info_plus_linux_plugin_test (using MemoryFileSystem to run Linux plugin on any host, coverage 0→100%), and device_info_plus_web_plugin_test (browser-side registerWith/constructor/deviceInfo). Android AndroidDisplayMetrics computed properties (57%→100%) and all BrowserName UA branches (38%→100%) were completed, and all 4 deprecated toMap() methods (Linux/Web/Windows/Base) reached 100% coverage. On the Demo side, device_info_coverage_demo.dart was added, exercising all 7 platform read paths and every field, invoked in main.dart's initState without UI rendering.

Boundaries that must be honestly stated: the remaining 13 lines cannot reach 100% on a single Windows host, and they are neither deprecated methods nor solvable by adding tests. The 7 lines in device_info_plus.dart are platform dispatch branches (kIsWeb compile-time constant, Platform.isAndroid/isIOS/... static getters that test code cannot mock—note that the getters themselves are already at 100%). The 6 lines in device_info_plus_windows.dart are the Win11 branch, registry-missing branch, and Win32 FFI throw WindowsException path (host-dependent and FFI cannot be injected). Achieving true 100% would require running on each platform's CI separately or extracting interfaces for injection (requiring lib/ source changes), both beyond the constraint of "only modify test/ and add demo files."

* Stability
The core stability fix is in DeviceMethodHandler.onMethodCall: previously, the entire method body had no try-catch and no result.error() calls whatsoever—once @ohos.deviceInfo property access threw an exception, call parameters were malformed, or deviceInfoAssemble()'s Promise was rejected, the Flutter layer would never receive a response (neither success nor error), the call would hang, and uncaught exceptions could crash the plugin process—completely breaking the ArkTS→Flutter exception propagation chain. This round added three layers of fallback: null/empty method name handling with INVALID_ARGUMENT, outer try-catch converting synchronous throws to UNHANDLED_ERROR responses, and .catch() on the async chain converting Promise rejections to DEVICE_INFO_ERROR responses. This guarantees that the Flutter layer always receives a definitive response under any circumstance, while the normal functional path (getDeviceInfo → success) remains completely unchanged.

Stability verification was also strengthened on the testing side: concurrency scenarios (10 concurrent calls, cache isolation), exception propagation scenarios (PlatformException bubbling up, repeated failures until recovery, cached values not polluted by errors from other getters). Fragile dependencies in Windows tests were also fixed: bare DateTime.now() comparison was changed to capture a before-time window, and buildLab assertions were changed from "strict prefix match on buildNumber" to regex matching (because BuildLab reflects baseline versions while buildNumber reflects patch versions—they become inconsistent after cumulative updates; the original assertion was a false positive on updated Windows systems).

* Code Quality
Critical: The method name DeviceInfoAssemble → deviceInfoAssemble violated camelCase and has been fixed (see Consistency dimension).

Honest nullability: The previous use of try-catch to wrap nonexistent serial/udid as "potentially successful system APIs" was an incorrect abstraction—now changed to not writing them + comments explaining why, aligning code intent with the platform's actual capabilities. Indentation chaos and try/catch nesting confusion caused by repeated lint modifications in DeviceMethodHandler have been reorganized and restored to a readable structure. Documentation comments now use proper @param/@returns/{@link} syntax rather than bare inline comments.
