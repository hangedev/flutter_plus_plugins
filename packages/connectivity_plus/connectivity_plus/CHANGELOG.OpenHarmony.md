## connectivity_plus-7.0.0-ohos.1.0.1 - 2026.9

### Fixed

* Consistency ([177](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/177)).
The core divergence between the OHOS implementation and Android/iOS centers on hasTransport. Android's getCapabilitiesList uses independent conditional checks to sequentially examine five transport types—WIFI, ETHERNET, VPN, CELLULAR, and BLUETOOTH—and can return multiple types simultaneously (e.g., WiFi+VPN). In contrast, the OHOS version returns immediately upon matching the first type, reporting only a single type when multiple networks coexist. This not only loses information but also violates the Dart layer contract of "returning a non-null List containing all matched types." A related issue is missing type support—while CONNECTIVITY_BLUETOOTH and CONNECTIVITY_VPN constants are defined in the code, they are never used in the judgment logic. Additionally, the other fallback present in both Android and iOS is absent, causing "connected but unknown type" to be misreported as none. Naming and terminology also diverge from upstream: getNetworkType() (singular) does not align with Android's getNetworkTypes() (plural), pluginBing is a spelling error, and constant visibility is inconsistent (none is public while others are private). All these issues have been fully resolved by rewriting hasTransport with independent checks, adding BEARER_VPN/BEARER_BLUETOOTH branches, introducing the other fallback, and unifying method names and constant visibility. Compilation verification has passed.

* Memory Leak ([177](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/177)).
The root cause is that Connectivity.netConnection is a static field, shared across all plugin instances. This NetConnection object holds five on() event callback closures for an extended period. These closures capture the receiver instance, and references to this within the closures form a complete circular reference chain, preventing the receiver from being garbage-collected even after the plugin is unloaded. This issue is exacerbated by incomplete cleanup paths: onCancel() only calls unregister() without clearing event subscriptions or nulling events, and onListen() can be invoked multiple times, causing listener accumulation and duplicate callbacks on every network change. The fix involved changing netConnection to an instance field to isolate subscription lifecycles, and refactoring the six event callback closures to capture only local variables within the method (netConn, connectivity, sink, flag) rather than this, thereby breaking the circular reference chain. A CancelFlag was introduced alongside unregister() to block in-flight callbacks after unregistration, and an isListening guard prevents duplicate registrations. It should be noted that the review initially flagged "absence of a corresponding off()" as a critical issue; however, after verifying the three SDK variants for API 12, the NetConnection interface provides only on(), register(), and unregister()—no off() method exists, and calling it would cause compilation failures. Therefore, the correct cancellation mechanism is unregister() (which stops all event triggers upon subscription cancellation), and this rationale has been documented in code comments.

* Documentation Quality ([177](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/177)).
Both English and Chinese README files contain multiple factual technical errors: the branch name was incorrectly written as a network_info_plus branch; the TAG spelling uses a hyphen, whereas the actual repository uses a period (the misspelled tag does not exist in Git); the return types for checkConnectivity and onConnectivityChanged are mislabeled as a single ConnectivityResult when the actual type is List<ConnectivityResult>; and the permission section lists only INTERNET while omitting GET_NETWORK_INFO, which is essential for querying network status. These errors are directly misleading to users and have been corrected one by one based on Git tags/branches, source code signatures, and SDK declarations. Additionally, referencing the CHECKLIST from the share_plus documentation review within the same monorepo, several structural deductions have been addressed: a table of contents was added, a standard version compatibility table including a "third-party library version" column was supplemented, runnable code examples were provided inline (rather than just link references), and the previously empty "Open Issues / Miscellaneous" section was filled. The only item not addressed within the two README files is the CHANGELOG entry for OpenHarmony changes, which belongs to a separate file.

* Test Coverage ([177](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/177)).
The original test suite only covered a single happy path for checkConnectivity. The onConnectivityChanged stream, its .distinct() deduplication behavior, the singleton pattern, ConnectivityPlusWebPlugin.registerWith() on the Web platform, and the two interfaces of DartHtmlConnectivityPlugin all lacked test coverage. Exception, edge-case, and concurrency scenarios were entirely missing, and tearDown was not used to clean up global platform instances. The main package and Linux implementation have been augmented by introducing a controllable fake platform that mocks both checkConnectivity and onConnectivityChanged. This enabled the addition of tests for singleton verification, exception propagation, concurrent checkConnectivity calls, multiple subscribers, distinct deduplication, network transition sequences, multiple connection types, other fallback, and connect exceptions, all with proper tearDown cleanup. Web-related tests could not be compiled under the Dart VM due to package:web 1.1.1 (missing toJS/jsify, and neither onPlatform nor Skip can bypass compile-time failures). These were addressed using conditional imports: placeholder tests run and are skipped under the VM, with assertions fully preserved for execution under Web runners—this is the standard approach for Flutter web plugin testing. flutter test --coverage passes fully, and the main facade class lib/connectivity_plus.dart achieves 100% line coverage.

* Stability ([177](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/177)).
The most critical stability issue is a broken exception propagation chain. Neither handleCheckResult nor getNetworkType includes try-catch blocks. When getDefaultNet or getNetCapabilities throws an error due to insufficient permissions or system exceptions, the exception is neither caught nor does result.error() get called, leaving the Flutter layer waiting indefinitely for a MethodChannel response. The register callback receives an error parameter but never checks it, so registration failures still proceed to retrieve the network type. Additionally, sendEvent returns a Promise that is always rejected, creating meaningless unhandled rejections. These issues have been fixed by catching exceptions inside getNetworkTypes and falling back to [none], wrapping handleCheckResult with an outer try-catch that calls result.error(), checking the error parameter in the register callback, and removing the fake rejected Promise while unifying the return type to void. As a result, exceptions on both the check and event pathways are properly contained, and the Flutter side consistently receives either a non-null result or a clear error code—no longer hanging due to unhandled exceptions.
