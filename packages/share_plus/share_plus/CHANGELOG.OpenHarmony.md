## share_plus-12.0.1-ohos-1.0.1 - 2026.9

* fix: Consistency ([179](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/179)).
The most concentrated issues are in platform behavior consistency. In the original code, isWithResult only recognized the *WithResult suffix, but the Dart side always calls the plain method names (share/shareFiles/shareUri) on OHOS, causing result tracking to be permanently disabled and always returning unavailable—inconsistent with Android's dismissed behavior. shareUri also returned a bare null instead of a sentinel string, preventing the Dart side from parsing the correct status. The handler called shareFiles with the title/subject parameters in the wrong order, which silently existed because the parameters lacked type annotations. getUniformTypeDescriptor only looked at file extensions, completely ignoring the mimeTypes passed from Dart, diverging from the MIME handling on Android/iOS; length consistency validation for paths/mimeTypes was also missing (iOS has it). The signature style used the deprecated List<string> instead of string[]. After fixes, the result-tracking semantics for the three methods are now isomorphic, and the shareUriWithResult case has been filled in. One item remains: the error code format uses 'share_error' on OHOS and 'Share failed' on Android—still inconsistent across platforms. Aligning them would require changes on the Android side or Dart-side mapping; the former is out of scope and the latter violates the "cannot modify lib" constraint, so it remains as-is without affecting functionality (Dart side transparently passes through the code).

* fix: Memory Leaks ([179](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/179)).
All four categories of leaks have been fixed. The first was that onDetachedFromEngine only cleared the channel, while the share instance (holding ApplicationContext and ability references) and methodChannelHandlerImpl were still held by the plugin after engine detachment—this was critical. Now a public dispose() method is exposed for unified release, and onDetachedFromAbility also calls it. The second was that dismiss listeners were registered with anonymous arrow functions, with no identical reference to pass to off(), causing both the listener and the closure-captured result to leak permanently. This was fixed by storing callback and controller references as fields, unregistering with the same reference after replying or on error, and tracking only for withResult paths (non-result paths have no callback and tracking would permanently block subsequent shares). The third was that fs.openSync() in fileIsInShareCache and copyToShareCacheFolder was never followed by closeSync(), causing file descriptor leaks; both now use try-finally to ensure closure even on exception paths. The fourth was that the cache directory is cleaned before each share, so accumulated content no longer lingers.

* fix:Documentation Quality ([179](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/179)).
The core defects in the two original READMEs: Chinese/English versions had copy-paste errors (leftover sensors_plus references); parameter signatures didn't match the actual lib code (shareUri had a non-existent title, share had title placed outside the optional-parameter braces, shareXFiles had an extra title); the 11 properties of ShareParams were completely omitted (missing forward-reference mapping); examples consisted only of a single link with no inline code, and all invocation approaches and HarmonyOS-specific behavior explanations were absent. After fixes, new sections were added: invocation guidelines (mutual-exclusion rules, required-field validation), six inline examples (text/URI/files/result handling/legacy API, each with HarmonyOS behavior annotations: system share panel, cache-directory copying, UTD mapping), a complete ShareParams property comparison table (verified item by item against what method_channel actually sends, marking yes/no—e.g., fileNameOverrides works on the Dart side so marked yes, previewThumbnail never goes over the channel so marked no), and a HarmonyOS platform-behavior differences section. Subsequent code changes (shareUri result tracking, concurrency limits, cache-cleanup failure reporting) were all reflected in the documentation to keep it in sync with implementation.

* fix:Test Coverage ([179](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/179)).
Coverage improved from 56.7% source / 60% demo to 100% on both. The constraints were to only modify files under test/, and for the demo only add files under example/lib and call them from main.dart without showing UI. Pitfalls encountered: calling Share.shareUri(validUri) or plugin.share(...) directly in the demo would genuinely bring up the system share panel/Web Share dialog, violating the "no UI displayed" requirement; this was fixed by using tear-off references (assigning the function itself rather than calling it). SharePlus.instance is a frozen static singleton bound to the real platform at class-load time, which cannot be bypassed, so coverage for Share.share('') / Share.shareXFiles([]) goes through the validation-layer error-throwing paths, and shareUri uses tear-off. The Web implementation uses _FakeRegistrar / _FakeUrlLauncher for registration and then restores the global instance. Remaining gap: OHOS native ArkTS code has no unit tests—.ets files cannot be tested with the Dart toolchain, and hvigor provides no test-framework integration for native code, so the native side can only be validated by compilation and manual testing on real devices. This is a structural blind spot in the current coverage system.

* fix:Stability ([179](https://gitcode.com/CPF-Flutter/flutter_plus_plugins/pull/179)).
The most severe issue was the forEach + async race condition in getUrisForPaths: Array.forEach does not await async callbacks, so uris always returned empty, completely breaking file sharing—this was a root-cause bug. After changing to an awaited for loop, the call was also moved into a try block (otherwise newly thrown exceptions become unhandled rejections and the Dart Future hangs). The exception-propagation chain was systematically broken: catch blocks in the handler and share() only logged and did not call result.error(), causing the Dart side to hang permanently. All were patched with if (withResult) guards for error replies, while also verifying path-by-path that result is replied exactly once (success/dismiss once, show failure once, concurrency rejection once, input-validation early-return once). Crash points: three title || subject! non-null assertions were changed to || subject || ''; text.length threw when text was null, so the signature was made nullable with a guard; the data! assertion was replaced with a null-check branch; critical fs API paths in copyToShareCacheFolder were wrapped with try. For robustness, an isSharing concurrency guard was added to prevent cache-directory races (note: the shareFiles delegation branch to share() must release the flag first, otherwise it gets blocked by its own guard).
